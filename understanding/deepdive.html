SECTION 01

Project brief and evaluation map

This is an original implementation of the supplied Zoom clone assignment. It assumes a default user is logged in, uses Next.js for the interface, FastAPI for the backend, and SQLite for persistent data. This guide is designed to help explain and demonstrate the implementation during the Scaler evaluation. It follows the criteria in the brief supplied in this chat; no additional Scaler rubric is assumed.

Useful interview introduction: “The app supports instant meetings, invitation-based joining, scheduling, and meeting history. The API stores meeting and attendance state in SQLite. For small live calls, browsers negotiate WebRTC peer connections using API-delivered signaling. Host controls use server-checked capabilities.” Treat this as a starting point to explain in your own words after reading the code.

The design follows Zoom's home actions, dialog patterns, and dark meeting toolbar. Architecture and separation of responsibilities

→
FastAPIValidation, authorization, lifecycle rules, state polling
→
SQLite / libSQLDurable rows, constraints, transaction boundaries
Presentation

Dashboard and room components render state. Shared UI handles dialogs, avatars, feedback, and copying.

Control path

JSON requests carry meeting data, chat, presence, host actions, and WebRTC signaling.

Media path

Audio/video move through peer connections, directly or via TURN. Python and SQLite do not encode media.

The Next.js App Router provides / for the dashboard and /j/[id] for an invitation room. Dashboard tabs and dialogs switch with React state, without full page reloads. The room is a separate client-side route. This gives the assignment's SPA-style interaction while preserving shareable URLs.

Locally, Next.js rewrites /api/v1/* to FastAPI on port 8000. On Vercel, top-level service rewrites route /api/* directly to the Python service. The browser uses relative API URLs in both cases. BACKEND_URL is the local proxy setting, not required for the checked-in cloud routing.

The backend retains durable state in tables rather than a Python dictionary of rooms. A new process can read that state. A process-local lock only protects initialization in that process; database constraints and transactions handle shared persistence. This distinction matters when multiple function instances serve requests.

SECTION 03

Frontend structure, state, and UX

Dashboard

Dashboard owns the loaded meeting list, selected navigation view, dialog state, scheduling input, join input, preferences, and feedback. Small helpers format dates, times, and IDs. Form handlers validate immediate input, call the API, and update the view. Home shows a compact selection; the Meetings view exposes a fuller searchable list and history.

The default identity is Alex Morgan. Profile, notifications, and help provide interface placeholders; they do not imply full account or notification infrastructure. Preferences are stored under zoom-preferences in browser local storage. They control initial mute, video, and whether to show the pre-join preview.

Reusable UI

components/ui.tsx contains Modal, Avatar, CopyButton, Busy, and Toast. Modal handling includes focus containment and Escape dismissal. Copying uses the Clipboard API with a fallback. Loading, validation, and operation feedback are shown near the relevant workflow.

State versus mutable resources

React state represents what should render: meeting data, participants, messages, errors, and media streams. Refs hold mutable resources such as peer connections and the current stream without triggering a render for every internal change. The peer map is keyed by participant UUID, so one remote participant corresponds to one connection.

API boundary and preview mode

lib/api.ts makes JSON requests to /api/v1, converts backend error responses into messages, and adds bearer authorization for participant actions. TypeScript contracts describe expected response shapes; they are not runtime validation of arbitrary server responses.

The demo adapter is enabled only when NEXT_PUBLIC_DEMO_MODE equals the literal string true. It was used to capture frontend designs before the backend existed. It stores preview data locally and supplies a single simulated participant. Real API mode reports failures instead of silently substituting demo data. Submission and backend tests must use real API mode.

Responsive and device behavior

The stylesheet adjusts navigation, dialogs, meeting grids, and toolbar layout for smaller screens. Browser checks verify mobile overflow in selected workflows. Media requires a supported browser and localhost or HTTPS. Permission denial is a normal state: the preview attempts camera/microphone, can fall back to audio, and permits joining with media off.

Design evidence: frontend_designs.pdf contains 25 desktop/mobile screenshots over 26 pages. They were captured in explicit preview mode and rendered for visual review. They document the UI, while live workflow tests provide functional evidence.
SECTION 04

Meeting lifecycle and core workflows

ScheduledFuture date and an unstarted session
→
ActiveInstant creation or a successful join
→
EndedHost ends or cancels; further joins rejected

1. Instant creation

  1. The dashboard sends a MeetingInput with no scheduled_at.
  2. Python generates an 11-digit ID using secrets.randbelow and a host capability using secrets.token_urlsafe(32).
  3. A transaction inserts both the meeting and its single session. Instant meetings are active immediately; the session start is creation time.
  4. The response returns public meeting fields and the raw host capability once. The browser stores it under zoom-host-<meeting-id> and opens /j/<meeting-id>.

The invite URL is built from the browser origin and meeting ID, so it works on localhost or the deployed domain. It never includes the host capability. The database's primary key prevents duplicate IDs; the pre-insert existence check makes collisions unlikely to affect normal use. A rare simultaneous collision could still fail the insert; there is no full insert-and-retry loop around that race.

2. Scheduling

The form captures topic, description, local date/time, and duration. It converts the local datetime to an ISO timestamp. Pydantic requires an explicit timezone and a future timestamp; the API normalizes it to UTC. Duration is 5–480 minutes, title 1–120 characters, description at most 2,000 characters.

The meeting is inserted with status scheduled; the session exists but its start time is null. The UI shows a confirmation with an automatically generated invitation. Reloading retrieves the persisted row. Duration is planning metadata, not an automatic timer that terminates the call.

3. Joining

  1. The join dialog extracts an ID from the input or invitation and checks the meeting through the API.
  2. The room loads public meeting details, applies saved preferences, and acquires device media for preview.
  3. Submitting a display name creates a new participant record and returns its bearer token. If this browser supplies the valid creator capability, the participant receives the host role.
  4. The atomic insertion checks available capacity and that the meeting has not ended. A successful join activates a scheduled meeting and fills the session start time if needed.
  5. The room starts state polling and discovers peers for WebRTC negotiation.

Scheduled rooms may be joined early. The API does not require the host to arrive first and has no waiting room. Rejoining creates a new attendance record rather than reviving the previous participant token.

4. Leaving, ending, and cancelling

Leaving sets only the participant's left_at; it does not end the room for others. A page-hide request attempts a keepalive leave, but abrupt crashes or network loss may prevent it. Heartbeat expiry handles stale participants.

Host ending updates meeting and session end times in one transaction. Clients learn the ended status during polling and close their media connections. Cancelling uses the creator capability before joining; active meetings must be ended from the room. Cancellation shares the ended status, so the schema has no separate cancelled lifecycle state.

SECTION 05

Database model: tables and relationships

backend/schema.sql is the schema source. IDs for meetings and users are text; sessions and participants use UUID-like text identifiers; signals and messages use increasing integer IDs. Media content is never stored in these tables.

Constraints

Meeting IDs must be exactly 11 numeric characters. Meeting status is restricted to scheduled/active/ended; duration is bounded. Participant flags are 0 or 1. Names and chat content must be nonempty after trimming. Foreign keys connect ownership and session data, with cascade deletion from meetings to sessions and sessions to room records. Participant deletion is not part of the normal leave workflow: attendance remains for chat attribution.

SQL foreign keys establish that referenced rows exist; they do not alone prove the sender and target share a session. The API validates that additional invariant for signaling and participant removal. Request models impose further field lengths and timezone rules that are not all duplicated by database constraints.

Indexes tied to queries

IndexQuery it supports
idx_meetings_schedule(status, scheduled_at)Lifecycle/schedule filtering. The current general list sorts by creation time, so this does not cover that sort.
idx_participants_presence(session_id, last_seen)Finding current participants and counting available room capacity.
idx_signals_target(target_id, id)Delivering signals addressed to one participant after its cursor.
idx_signals_age(created_at)Removing expired signaling events.

Seed behavior

The default user is always inserted idempotently. Unless sample seeding is disabled, three upcoming and two ended meetings use fixed IDs and INSERT OR IGNORE. New initialization does not duplicate them or reset existing rows. Their dates are relative to the first insertion; repeated initialization does not continually move them into the future. Their host secret hashes are generated without exposing a recoverable host capability.

SECTION 06

Transactions, concurrency, and hosted persistence

Local SQLite

Database.batch opens a connection, enables foreign keys and WAL, begins BEGIN IMMEDIATE, executes parameterized statements, commits, and closes. On failure it rolls back the complete batch. WAL helps reader/writer coexistence, but SQLite still serializes writers. The connection timeout is 15 seconds.

Even execute wraps a single statement in the same transaction abstraction. This makes behavior consistent, but read-only operations also use immediate transactions, which can add writer contention at higher load.

Atomic capacity

A naive “count, then insert” in separate requests can admit too many participants. The actual insertion uses INSERT ... SELECT ... WHERE with a count of active, nonremoved, nonleft participants in the same transaction. It also rechecks the meeting is not ended. The following is a shortened explanation of that predicate, not the full source query:

INSERT INTO participants (...) SELECT ...
WHERE (
  SELECT COUNT(*) FROM participants
  WHERE session_id = ? AND removed = 0 AND left_at IS NULL
    AND last_seen > ?
) < 6
AND EXISTS (
  SELECT 1 FROM meetings WHERE id = ? AND status <> 'ended'
)
RETURNING *;

The following status/start updates are conditional on successful participant insertion. If no row returns, the API reports a full or ended room. A backend test attempts eight concurrent joins and verifies only six succeed.

Hosted libSQL transport

On Vercel, TURSO_DATABASE_URL and TURSO_AUTH_TOKEN select the hosted path. The adapter sends typed SQL parameters over HTTPS to Hrana /v2/pipeline. It first enables foreign keys, then sends a batch with begin, application statements, conditional commit, and conditional rollback. Each step depends on the previous step's success, so a failed statement does not allow later writes to commit.

Returned columns and typed values are converted to dictionaries with Python null/integer/float/text values. The rest of the API receives the same result shape locally and remotely. SQL and schema are shared; storage transport changes. The implementation follows the libSQL HTTP v2 specification.

Durability safeguard: When the VERCEL environment variable is present and no hosted database URL is set, the adapter raises an error instead of silently writing temporary local files. A successful local build does not prove cloud durability.

What is not transactional across the entire request

Each batch is transactional; an entire endpoint can contain several batches. Authorization, target checks, and a later action are not always one atomic operation. Concurrent moderation or lifecycle changes can therefore have time-of-check/time-of-use windows. A production refinement would combine relevant checks and writes in guarded statements or one transaction.

Schema initialization uses CREATE ... IF NOT EXISTS, not a versioned migration system. This is sufficient for the initial assignment schema. Future schema changes need explicit migrations rather than assuming initialization will alter existing tables.

Validation and errors

The shared Pydantic input configuration strips surrounding whitespace and forbids unknown fields. Clients cannot send is_host through the update model. Name length is 1–60, chat is 1–2,000 characters, and signaling kind is restricted to offer/answer/ice. Signal JSON is checked against a 100,000-character serialized payload limit.

Expected HTTP errors include 401 for missing/invalid participant tokens, 403 for host-only actions or expired/removed attendance, 404 for missing meetings or targets, 409 for lifecycle/capacity conflicts, 413 for oversized signaling payloads, and 422 for Pydantic validation failures. A RuntimeError from database setup/transactions becomes a generic 503. Some transport exceptions can still follow FastAPI's generic error path rather than that handler; do not claim every possible failure has a custom response.

SQL values use bound parameters. Dynamic column names in participant updates come only from the validated model field names, not arbitrary raw request strings. API responses use explicit public-field projection and Cache-Control: no-store.

SECTION 08

Identity, capabilities, and host permissions

There is no login/signup. The default user owns newly created meetings, but meeting ownership in a database row is not enough to grant the browser host actions. The creator must possess that meeting's random capability.

CredentialStored wherePurpose
Creator / host capabilityRaw value returned once; creator browser localStorage. SHA-256 hash in meetings.Proves ability to join as host or cancel before entering.
Participant bearer tokenRaw value in current room client state. SHA-256 hash in participants.Authenticates a specific join for polling and room actions.
Turso database tokenBackend deployment environment only.Authorizes hosted SQL transport; never belongs in browser configuration.
TURN credentialFrontend ICE configuration in this implementation.Allows relay use; visible to browsers and therefore must be scoped.

Joining compares the SHA-256 digest of the submitted creator capability to the stored hash using secrets.compare_digest. If valid, the server sets is_host on the new attendance record. If an explicitly supplied creator token is wrong, the request fails instead of silently becoming a guest.

For room actions, the authorization dependency hashes the bearer and queries a participant joined to the requested meeting's session. It then checks removal, leave time, and heartbeat age. This binds a token to a particular meeting; a token for room A cannot operate on room B. Host endpoints additionally inspect the stored is_host flag.

SHA-256 here hashes high-entropy random capabilities, not human passwords. Those are different threat models. An invite ID is public and is not an authorization secret. Meeting lists and invite URLs do not expose capability hashes or raw tokens.

Limits to explain honestly: Capability possession is the identity model. Browser localStorage is readable by scripts from that origin; XSS would threaten stored host capabilities. A removed guest can create a new attendance identity through the public invite. Multiple joins possessing the creator capability can be hosts. There are no durable bans, account isolation, rate limits, or a production authentication system.

Host mute-all is client-cooperative moderation: the backend persists the muted flag, then the normal guest client disables its actual audio track when polling sees it. A modified client could ignore the instruction or unmute. This is not media-server-enforced moderation.

SECTION 09

WebRTC: how real audio and video connect

lib/use-meeting.ts owns the live connection logic. Each browser creates one RTCPeerConnection per other current participant. The room is a mesh: six participants mean 15 pairwise connections total and up to five outgoing peer paths per participant.

Step-by-step negotiation

  1. Joining returns the local participant UUID and bearer. Polling discovers other active participants.
  2. For each pair, the lexicographically smaller participant UUID is the caller. Only this side creates the initial audio and video transceivers and an SDP offer.
  3. The offer is stored as a signal addressed to the other participant. The other browser retrieves it through state polling.
  4. The answering browser applies the remote description, binds its local audio/video tracks to the transceivers created by that offer, sets direction to sendrecv, creates an answer, and sends it back.
  5. The caller applies that answer. Both browsers exchange ICE candidates through the API as candidates become available.
  6. WebRTC selects a viable candidate pair, establishes its media transport, and delivers remote tracks through ontrack.
CallerOffer + ICE → addressed API signals
→
AnswererApply offer; bind tracks; answer + ICE
→
Both peersDirect or relayed bidirectional media

What each term means

SDP describes media capabilities and transport negotiation. ICE tries candidate network paths. STUN helps find reachable addresses. TURN relays media if a direct route cannot be established. Signaling is the application's delivery mechanism for negotiation metadata; WebRTC does not dictate which HTTP routes or database to use. See the primary WebRTC peer connection guide.

Two subtle correctness choices

Offer glare: If both browsers create offers simultaneously, their signaling states can conflict. The deterministic UUID ordering selects one caller per pair and avoids the initial simultaneous-offer problem. It is a small-room strategy, not a full implementation of every renegotiation scenario.

Transceiver ownership: Creating independent transceivers on the answer side before applying the remote offer can leave outgoing tracks attached incorrectly and produce one-way media. The implemented answer path binds local tracks to the offered transceivers after setRemoteDescription. Real two-way browser testing caught and verified this distinction.

ICE ordering and stream updates

Candidates can arrive before a remote description is ready. A per-peer pendingIce queue buffers them and flushes after the offer or answer is applied. Signal IDs advance a client cursor after processing, preventing already handled events from being returned repeatedly in normal operation.

The hook keeps the current stream in a ref. When it changes, existing senders replace the track matching their negotiated kind. Remote tracks are assembled into a MediaStream for each tile. Connection-state changes update the rendered connection status; peers that leave the current participant list are closed and removed.

Scale and failure boundaries

Mesh upload/encoding load grows with participant count, so the API limits the room to six active participants. This is suitable for the assignment's small rooms. Large conferencing requires an SFU/media server, bandwidth adaptation, more resilient connection recovery, and enforced moderation. There is no explicit ICE restart strategy or automatic rebuild of a failed peer in the current hook.

SECTION 10

Devices, controls, and cleanup

Pre-join media

MeetingRoom calls getUserMedia to request audio/video and shows the local preview. If that fails it attempts an audio-only fallback. If access is denied or unavailable, it sets an explanatory state and allows a participant to enter without media. The browser's permission prompt remains the user's decision.

A mounted ref guards asynchronous acquisition. If a permission prompt resolves after the component has unmounted, the newly returned tracks are stopped instead of leaving capture running. Local video is muted to avoid playing the user's microphone back to themselves; remote feeds carry the remote audio.

Mute and video off

The UI updates actual track enabled flags and posts the corresponding participant state. Disabling a track keeps the negotiated connection but suppresses its content. The guest also observes server mute-all state and disables its microphone. The database flag is for synchronization; it is not itself an audio signal.

Screen sharing

getDisplayMedia asks the browser to let the user select a source. The captured video track replaces the outgoing camera video track through sender replaceTrack. The audio track remains the microphone. Stopping share restores camera video. The implementation shares one video source per participant; it does not send camera and screen as two simultaneous independent video feeds or implement separate system-audio sharing.

Resource cleanup

On leave, end, removal, expiry, or unmount, the room/hook stops applicable local capture and closes peer connections. The polling timeout is cleared on hook cleanup. A stopped flag avoids applying a late polling result after cleanup. Screen-sharing track lifecycle is handled so that stopping capture returns the UI to the camera.

Browser page-hide sends a keepalive leave request where possible, but servers cannot rely on this firing. Stale heartbeat logic covers unclean departure. Permission support, background throttling, and network conditions still vary by browser and device, which is why public deployment must be tested physically.

SECTION 11

Presence, chat, signaling, and consistency

Each successful state request updates the caller's last_seen, retrieves the current roster, fetches new target signals after its cursor, reads the latest 100 chat messages, deletes signals older than five minutes, and returns meeting status. A normal poll is scheduled about one second after the previous attempt completes.

RuleCurrent valueImplication
Presence lifetime60 seconds without heartbeatCrashed/disconnected clients disappear from active counts. An expired bearer must rejoin.
Polling delayAbout 1 second; failure delay grows to 5 secondsChat, hands, mute-all, and roster changes are eventually visible, not instantaneous.
Signals per state responseUp to 200 newer addressed eventsCursor-based catch-up. Old negotiation data is not retained forever.
Signal retentionFive minutes; cleanup during state pollingSuitable for fresh negotiation, not a permanent audit log.
Chat windowLatest 100 messages in chronological orderOlder messages remain stored but there is no UI pagination for them.
Meeting listLatest 250 records by creation timeNo general pagination or arbitrarily large history browser.

Polling keeps this implementation compatible with stateless request handlers and persisted room state. It was a deliberate implementation choice; do not explain it by claiming every hosting platform categorically lacks WebSocket support. An event-driven signaling service could reduce latency and repeated reads/writes.

Each active participant produces roughly one state request per second plus action and signaling requests. The state endpoint performs several SQL operations and a heartbeat write. At six participants that means roughly six recurring requests per second for one room, before network latency. Many rooms require more efficient push updates, presence storage, retention jobs, and capacity planning.

Chat has no optimistic server acknowledgment object: posting returns success, and the next state response supplies the saved messages. Sender attribution comes from the authorized participant, not a client-submitted author name. Hand-raise is a permitted participant flag. Server-ended status and rejected removed/expired tokens close the client room; ordinary transient errors show feedback and retry.

SECTION 14

Interview questions and code-reading exercises

Read the answers, then close them and explain each point aloud with the source open. The assignment requires understanding every line submitted; this guide is a map for that work, not a substitute for reading and running the code.

Why separate meetings and sessions if the relation is one-to-one?

A meeting contains invitation/schedule metadata; a session captures actual attendance timing. Separating them keeps those concepts distinct. This assignment enforces one session with a unique meeting FK. Supporting repeated occurrences would remove that one-to-one constraint and add an occurrence model.

What prevents two concurrent joins from exceeding capacity?

The room count and conditional participant insertion run inside the same immediate transaction. Subsequent lifecycle updates depend on the inserted participant. Show the guarded INSERT in join_meeting and the concurrent test where eight attempts result in six successes.

Does the invitation link grant host privileges?

No. It contains the public meeting ID only. The creator browser separately stores a random capability returned once. A valid capability grants a joined participant its server-stored host flag; room actions then use that participant's bearer token.

Why can a removed user join again?

Removal invalidates the current attendance session, not a durable account. There is no authenticated guest identity. A public invite can create another participant record. Persistent bans require a different identity and policy model.

How does the browser know whom to call?

State polling returns the current roster. The hook creates one peer per other participant. UUID ordering selects a single caller in each pair, and addressed signals carry the offer, answer, and ICE candidates.

Why buffer ICE candidates?

A candidate may arrive before setRemoteDescription has run. Applying it too early can fail. The hook buffers candidates by peer and flushes them after applying the remote offer or answer.

What was the one-way-media bug, and why does the answer path matter?

The answerer must bind its local tracks to transceivers negotiated by the offer, not create unrelated senders that remain disconnected from those media sections. The current implementation applies the offer, replaces tracks on the resulting transceivers, sets sendrecv, and then creates the answer.

Where do video packets go, and why is SQLite not a bottleneck for those packets?

Media goes over browser peer connections directly or through TURN. SQLite stores control/signaling metadata. It can still bottleneck the many heartbeat and signaling requests, but it does not store the video stream.

What does screen sharing change?

The browser acquires a display video track and replaces the outgoing video sender track. The microphone remains audio. Stopping share restores the camera. It is one video source per participant, not two simultaneous camera-plus-screen feeds.

Why not write a local SQLite file on Vercel?

Serverless instances/deployments cannot be treated as one durable local database volume. The adapter requires hosted libSQL there and uses the same SQL schema over HTTPS. The VERCEL guard rejects a missing hosted configuration.

How do UTC dates and local display work?

The form turns local input into an ISO timestamp; validation requires timezone information and a future time. The backend stores UTC. Browser formatting converts it back for that browser's locale/timezone. Duration does not schedule an automatic end.

What do the tests prove about real calls?

Two independent Chrome processes exchanged audio and video verified through inbound statistics, using generated media inputs. This proves negotiation and transport locally. It does not prove physical device behavior or cross-network relay reachability; those require manual deployed checks.

How would you scale this?

Replace mesh with an SFU, use event-driven signaling/presence, add account auth and moderation, reduce SQL polling load, introduce migrations and pagination, and test recovery. Start by measuring concurrent-room load rather than assuming this small-room design scales unchanged.
