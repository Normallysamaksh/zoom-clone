How to deploy

A step-by-step handoff for running locally, publishing the source, and deploying the complete Next.js + FastAPI application on Vercel with persistent SQLite.

SECTION 01

What you will deploy

This project has a Next.js frontend, a FastAPI backend, and a SQLite schema. The checked-in deployment configuration runs the frontend and backend as two services in one Vercel project. Your friend can unzip the source, install dependencies, and run it locally before publishing.

Current status: The app is implemented and tested locally. A public GitHub repository and a live Vercel/Turso deployment have not been created or tested. This document is the procedure for completing those submission steps.
BrowserDashboard, pre-join, meeting room
→
VercelNext.js for pages; FastAPI for /api/*
→
Turso / libSQLPersistent hosted SQLite for meetings and signaling

Audio and video use WebRTC between participants, directly or through a TURN relay. They do not travel through the database. Hosted SQLite is required by the backend when running on Vercel; uploading a local .db file is not the deployment approach.

Vercel documents multi-service projects and service-based routing in its Services overview and routing reference. The configuration below follows those interfaces. Check those references if the dashboard changes.

Accounts

GitHub, Vercel, and Turso/libSQL. A TURN provider or relay is useful for testing across networks.

Local tools

Node.js 22+, Python 3.12+, Git, and Chrome for the included browser tests.

Submission

Public repository URL and public app URL. Confirm both open without your account.

SECTION 02

Unzip and run locally

  1. Extract zoom_clone_project.zip. Open the terminal inside its zoom_clone folder, where package.json and vercel.json live.
  2. Install the frontend and Python dependencies, then copy the safe environment template.

Windows PowerShell

npm ci
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r backend/requirements-dev.txt
Copy-Item .env.example .env.local
npm run dev

Activating the virtual environment is optional: the launcher automatically uses .venv. If PowerShell blocks npm.ps1, use npm.cmd for npm commands.

macOS / Linux

npm ci
python3 -m venv .venv
.venv/bin/python -m pip install -r backend/requirements-dev.txt
cp .env.example .env.local
npm run dev

Open http://127.0.0.1:3000. The launcher starts FastAPI on port 8000 and Next.js on port 3000. API documentation is at http://127.0.0.1:8000/api/docs. Stop the launcher with Ctrl+C.

The first API request initializes the schema and default user, with three upcoming and two completed sample meetings. Local data defaults to data/meetings.db. The ZIP intentionally contains no local database; seed data comes from backend/seed.py.

Confirm it is using the real backend

BACKEND_URL=http://127.0.0.1:8000
NEXT_PUBLIC_DEMO_MODE=false

These values belong in your local .env.local. Preview mode is only for capturing designs. It uses browser storage and does not provide a live multi-person call or prove backend persistence.

SECTION 03

Run the project checks

Keep both development servers running for the browser tests. In a second terminal at the project root, run:

.venv\Scripts\python.exe -m pytest
npm run typecheck
npm run test:e2e
npm run build

On macOS/Linux use .venv/bin/python -m pytest. Chrome must be installed: the Playwright configuration explicitly uses the Chrome channel. Unit tests use isolated databases; browser tests create meetings in your running local API.

SECTION 04

Create the public GitHub repository

The ZIP contains source, lockfiles, tests, README, validation notes, frontend screenshots, and frontend_designs.pdf. It excludes these two HTML documents, environment secrets, installed dependencies, build output, caches, and local databases.

  1. On GitHub, create a new repository and set visibility to Public. Choose a repository name, for example zoom-meeting-platform.
  2. If using the commands below, create an empty repository without initializing a README, license, or gitignore. Those choices can otherwise produce an initial-history conflict.
  3. Run these commands from the extracted project root. Replace the example URL with your actual repository URL.
git init -b main
git add .
git status --short
git diff --cached --stat
git commit -m "Build Zoom meeting platform"
git remote add origin https://github.com/YOUR_USERNAME/YOUR_REPOSITORY.git
git push -u origin main
Before the commit: Review the staged filenames. .env.example should be included; .env.local, database files, node_modules, and .venv should not. The extracted ZIP already omits both HTML guides. Upload the extracted project files, not the ZIP itself, so Vercel can find the application.

If Git asks for your identity, set your own name and email using Git's configuration. GitHub may require browser authentication or a token. Never put a GitHub token in the source or the remote URL. This guide does not publish anything automatically.

SECTION 05

Create persistent hosted SQLite

Use a Turso/libSQL database that supports SQL over the Hrana HTTP v2 pipeline. backend/db.py connects to /v2/pipeline, using the database URL and a write-capable authentication token. It runs the same schema and parameterized SQL used locally.

  1. Sign in to Turso and create a database dedicated to this assignment. Choose a region close to the backend where practical.
  2. Copy its database connection URL, such as libsql://your-database.turso.io. The backend converts the scheme to HTTPS.
  3. Generate a database token with write access. The application must create tables and persist meeting state, so a read-only token will fail.
  4. Keep both values for the Vercel environment settings. You do not need to upload a prebuilt database or manually run the schema.

If you already have the Turso CLI installed and authenticated, equivalent commands are:

turso db create zoom-meetings
turso db show zoom-meetings
turso db tokens create zoom-meetings --expiration 30d

Copy the URL from the database details and the token from the token command. Choose a token lifetime that covers the evaluation, and renew it before expiry. See the official database creation and token creation references for CLI options.

Keep production and preview separate: Preview deployments using the same database can create test meetings or modify live state. Prefer a separate preview database and separate credentials. Setting SEED_SAMPLE_DATA=false prevents new sample inserts; it does not delete existing records.
SECTION 06

Import into Vercel and configure services

  1. In Vercel, add a new project and import the public GitHub repository.
  2. Use the repository root as the project root. Keep backend/ as the backend service root through the checked-in configuration; do not change the entire project root to that folder.
  3. Allow the checked-in vercel.json to define the services and routing. Choose Node.js 22 or newer where the runtime selection is available. Python dependencies and the entrypoint are declared in backend/pyproject.toml.
  4. Add the environment variables in the next section before deploying. If the first automatic deployment runs before configuration is complete, add the values and redeploy.
  5. Review the build logs and verify that both frontend and backend are built.

The configuration already included in the project

{
  "$schema": "https://openapi.vercel.sh/vercel.json",
  "services": {
    "frontend": { "root": ".", "framework": "nextjs" },
    "backend": {
      "root": "backend",
      "framework": "fastapi",
      "entrypoint": "main:app"
    }
  },
  "rewrites": [
    { "source": "/api/(.*)", "destination": { "service": "backend" } },
    { "source": "/(.*)", "destination": { "service": "frontend" } }
  ],
  "headers": [
    {
      "source": "/(.*)",
      "headers": [
        { "key": "X-Content-Type-Options", "value": "nosniff" },
        {
          "key": "Referrer-Policy",
          "value": "strict-origin-when-cross-origin"
        },
        {
          "key": "Permissions-Policy",
          "value": "camera=(self), microphone=(self), display-capture=(self)"
        }
      ]
    }
  ]
}

The first rewrite sends /api/* to FastAPI, retaining the original path. The final rule sends other requests to Next.js. Its order matters. Backend routes therefore remain /api/v1/...; do not strip the /api prefix. See Vercel's service routing reference.

No global custom build or output directory is required by this repository. Keep each service's framework defaults. If a project override conflicts with Services, remove that override or move the relevant setting to its service as described in the Services documentation.

Runtime behavior: Vercel runs the Python application as a backend service. Do not use npm run dev or npm run start:all as the cloud launch command; those scripts coordinate local processes.
SECTION 07

Set environment variables correctly

Use Vercel project environment settings and ensure the variables reach the indicated service. If your dashboard offers service scopes, assign them as shown; with shared project settings, keep database values server-only and never prefix them with NEXT_PUBLIC_. Enable the relevant Production and Preview environments, with separate database values where possible.

VariableConsumerValue / action
TURSO_DATABASE_URLBackendRequired on Vercel. Your database URL, beginning libsql:// or https://.
TURSO_AUTH_TOKENBackendRequired. Write-capable database token; server-only secret.
NEXT_PUBLIC_DEMO_MODEFrontend buildUnset or false. Do not submit a design-preview deployment.
NEXT_PUBLIC_ICE_SERVERSFrontend buildOptional JSON array of STUN/TURN servers; recommended for cross-network calls.
BACKEND_URLLocal frontend onlyLeave unset on Vercel for the checked-in two-service configuration.
SEED_SAMPLE_DATABackendOptional; defaults to true. Creates sample meetings idempotently.
DATABASE_PATHLocal / persistent hostNot used for durable storage on Vercel. Defaults to data/meetings.db locally.
ALLOWED_ORIGINSBackendOptional comma-separated origins for a frontend calling the backend across domains. Same-domain Services routing needs no cross-origin request.
PYTHON_EXECUTABLELocal launcherOptional override if your Python executable has another name or location.

After changing variables, redeploy. NEXT_PUBLIC_* values are compiled into browser code, so changing them requires a new frontend build. Never upload .env.local or share it with your friend as part of the project.

Why BACKEND_URL must be absent: The local value points to 127.0.0.1:8000. A deployed frontend cannot reach your laptop through that address. Public requests already reach FastAPI through vercel.json.
SECTION 08

Configure calls across different networks

The current default is one STUN server. STUN helps browsers discover possible network paths; a TURN relay provides a media path when direct connections are blocked. A dashboard that loads correctly is not evidence that two devices on different networks can communicate.

Obtain TURN server URLs and scoped credentials from your relay/provider, then set the frontend variable NEXT_PUBLIC_ICE_SERVERS to a JSON array in this shape:

[
  { "urls": "stun:stun.l.google.com:19302" },
  {
    "urls": [
      "turn:YOUR_RELAY_HOST:3478?transport=udp",
      "turns:YOUR_RELAY_HOST:5349?transport=tcp"
    ],
    "username": "YOUR_SCOPED_USERNAME",
    "credential": "YOUR_RELAY_CREDENTIAL"
  }
]

Use the URLs, ports, and transports your provider actually supports. Paste valid JSON with double quotes; do not add an outer pair of quote characters in the Vercel value field. Redeploy after changing it.

Public credential limitation: This implementation reads ICE configuration at frontend build time. Every browser can inspect it. Use scoped, limited-lifetime credentials and remember that expiry requires replacement and a rebuild. A production system should issue short-lived TURN credentials from an authenticated backend; that endpoint is not implemented here.
SECTION 09

Verify the deployed app before submission

Replace YOUR_APP with the deployed hostname. Open https://YOUR_APP.vercel.app/api/v1/health. The expected response is:

{ "status": "ok", "database": "hosted-sqlite" }

This route initializes the schema and seed data through the API dependency. It confirms database setup on a newly initialized backend, but does not by itself verify media or prove every later database request will succeed.

For host tests, create your own meeting. Seeded upcoming rooms are joinable as guests and deliberately do not reveal their host secrets. A second tab in the same browser may reuse the same host capability; use a separate profile or device to test a real guest.

SECTION 10

Troubleshooting and a fallback deployment

SymptomLikely cause / next action
Dashboard appears, but meetings cannot loadOpen /api/v1/health, inspect backend runtime logs, and confirm Turso variables and write permissions. The UI does not silently fall back to demo data.
API path returns Next.js HTML or 404Check that the API rewrite is first and points to the backend service. Confirm the repository root and both service builds.
Database unavailable / backend errorCheck URL scheme, token presence and expiry, write access, and hosted database reachability. The runtime refuses ephemeral local SQLite on Vercel.
Changes vanish on another browserCheck that demo mode is false. Design-preview data lives in browser storage. For live mode, confirm the API returns hosted SQLite.
No host controlsThe creator browser holds the host token. Seeded rooms and a different browser are guests. Create a fresh meeting in this browser.
Camera / microphone unavailableUse HTTPS or localhost. Check browser and OS permissions, devices, and whether another app owns the camera. Join without media if needed.
Peers join, but remote media is absentCheck the ICE JSON, TURN reachability and expiry, and test a different network. Use browser WebRTC diagnostics to inspect candidate-pair and inbound media statistics.
Session expired after inactivityPresence expires after 60 seconds without heartbeat. Rejoin. Background browser throttling or network loss can interrupt polling.
Scheduled meeting absent from HomeHome is a compact view. Open the full Meetings list and search for its title. Ended/cancelled rooms belong to history.
Local port already in useStop another local app instance before launching. Keep development and production launchers from competing for ports 3000 and 8000.

Fallback: Vercel frontend plus a persistent Python host

If you prefer a separate backend host, use a Python service with a persistent volume for SQLite, or continue using hosted libSQL. Replace the two-service vercel.json with a Next.js-only configuration and retain any suitable headers. Set the Vercel frontend's BACKEND_URL to the backend's public HTTPS origin, with no trailing /api/v1. Next.js will proxy that prefix through its existing rewrite. Redeploy after changing it.

On the Python host, install backend/requirements.txt and run python -m uvicorn backend.main:app --host 0.0.0.0 --port <HOST_ASSIGNED_PORT> from the repository root. If using local SQLite there, set DATABASE_PATH to the mounted persistent disk. Keep the backend available during evaluation, and check that host-specific sleeping or disk behavior will not interrupt the demo. This alternative has not been deployed or verified either.

Final handoff

Send your friend the ZIP and the deployment guide separately. The repository source retains README.md for setup and VALIDATION.md for test evidence. Save credentials only in the relevant host's environment settings. The screenshots PDF is included as a design artifact.
